Architecture

Three interlocking enforcement layers.

Each layer has a distinct role. Together they make it structurally impossible for an agent to violate policy — regardless of what it's told.

Layer 01
Tether
Policy Gate · OPA / Rego
Every tool call is evaluated against your Rego policies before execution. ALLOW, escalate to HITL, or BLOCK — decided in under 8ms. Policies are version-controlled code, not config files.
Layer 02
Anchor
HITL Queue · Async by default
High-risk actions are escalated to a human reviewer before execution. The agent waits asynchronously — no unsafe fallback, no timeout bypass. Every approval is logged with reviewer identity and timestamp.
Layer 03
Sandbox
Container Isolation · Docker / Firecracker
Each agent session runs in an isolated container with no egress by default. One compromised session cannot reach another. Firecracker MicroVM provides hardware-enforced isolation in production.
Enforcement model

Five risk tiers. One policy engine.

Every action is classified at evaluation time. Tier determines the default enforcement outcome — and you can override any default per action in Rego.

Tier Name Examples Default outcome
01 INFORMATIONAL Read customer record, list transactions, status lookups ● Auto-allow
02 OPERATIONAL Update record, send notification, write to memory ● Allow with scope
03 TRANSACTIONAL_HIGH Approve refund > $1000, wire transfer, contract execution ● HITL escalation
04 DESTRUCTIVE Delete records, bulk operations, drop table, revoke access ● HITL or block
05 SECURITY_CRITICAL Shell exec, credentials access, file system ops, network sockets ✕ Hard block
Policy-as-code

Rules your compliance team
can actually read.

Policies are Rego files — version-controlled, peer-reviewed, tested in CI. Not a vendor config dashboard. Your rules, in code, under your control.

policies/financial.rego

        

      

      

        

          

          

            
Version-controlled and auditable

            
Every policy change is a git commit. Diffs show exactly what changed and when. Compliance teams can review and approve rule changes like any other code.

          

        

        

          

          

            
Policies have unit tests

            
Write Rego tests alongside your rules. Run them in CI. Know before deploying that your policy handles the edge cases your agent will find.

          

        

        

          

          

            
Evaluated in <8ms per call

            
OPA evaluates policies in-process. The policy gate adds single-digit milliseconds per tool call — enforcement without observable latency cost.

          

        

        

          

          

            
Deny-by-default, always

            
Every policy file starts with default allow := false. Actions are blocked unless a rule explicitly permits them. No accidental open door.
